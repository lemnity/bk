# Rules — правила разработки (для людей и AI-агентов)

Обновлено: 2026-10-27. Устройство проекта — [architecture.md](architecture.md).

## 1. Перед началом

- Прочитать [PRD.md](PRD.md), [architecture.md](architecture.md), [memory.md](memory.md) (открытые вопросы
  и решения), для UI — [design.md](design.md) и [admin-design-system.md](admin-design-system.md).
- Найти существующий модуль и паттерн, прежде чем писать новый. Не дублировать логику: модель отчёта —
  в `admin-report-doc.js`, HTML письма — в `toHtml`, состояние — в `AdminStore`.
- Крупная работа — через спецификацию и план в `docs/superpowers/` и задачи в [tasks.md](tasks.md).

## 2. Код

- Без сборки и зависимостей: plain `<script>`, IIFE, `"use strict"`, один `window.<Имя>` на модуль.
- Комментарии по-русски, объясняют **почему**, в стиле существующих файлов.
- **Кеш-бастинг:** новый файл подключается с `?v=1`; при правке файла его `?v=N` увеличивается на 1
  **на всех страницах**, где он подключён. Проверка:
  `grep -rho 'admin.css?v=[0-9]*' --include='*.html' . | sort | uniq -c` — версия одна.
- Порядок скриптов на `report.html`: store → data → kinds → reports → specs → doc → view.
- Не трогать JS-хуки (id и классы, на которые ссылается JS) при правке стилей.
- Никаких `alert()` / `confirm()` / `prompt()` — только `AdminDialog`.

## 3. Данные и безопасность

- Всё, что пришло из стора, формы или файла, экранируется при выводе в HTML (`esc`) или ставится через
  `textContent`.
- Пользовательский HTML показывается только в `<iframe sandbox="">` (без `allow-scripts`).
- Ссылки в письмах — только `http(s)`, `mailto`, `{{переменная}}` (`safeHref`).
- Демо-данные детерминированы: никаких `Math.random`/`Date.now` в генерации.
- Выгрузки и копии = то, что на экране (снимок модели, а не повторная сборка из формы).
- Пустой результат — понятное пустое состояние, выгрузки неактивны.

## 4. Тесты и готовность задачи

- Каждое изменение поведения — смоук в `tests/` (Python Playwright): реальный ввод (`fill`, клавиатура),
  без синтетических событий и пропускаемых `if`-проверок; ожидание асинхронного UI — через `expect(…)`.
- Перед коммитом — **все** тесты: `for t in tests/*.py; do printf "%s: " $t; python3 $t | tail -1; done`.
- Задача готова, когда: тесты зелёные, версии `?v` согласованы, UI проверен глазами (скриншот), нет
  ошибок консоли, документация обновлена (этот набор + план в `docs/superpowers/plans/`).

## 5. UI и доступность

- Только токены и компоненты из `admin.css` / `styles.css`; новые hex-цвета вне `:root` запрещены.
- Классы с префиксом модуля: `rv-`, `rdoc-`, `rep-`, `lt-`, `mv-`, `ml-`, `dlg-`, `af-`, `sp-`.
- Видимый фокус, контраст AA (`--ink-mute` светлее не делать), интерактив — `<button>`/`<a>`,
  `aria-*` у меню и диалогов, Esc закрывает, фокус возвращается.
- `prefers-reduced-motion` отключает анимации.
- Тексты интерфейса — по-русски, в тоне кабинета; ошибки — у поля, с подсказкой, что сделать.

## 6. Git

- Коммиты по-русски, по одному на смысловую единицу.
- Крупная работа — в отдельной ветке (worktree), слияние в `main` через `--no-ff` после зелёных тестов
  на результате слияния. Пуш в `main` публикует сайт — только с согласия владельца.
- Не коммитить `.superpowers/`, `node_modules/`, `.vercel`.

## 7. Поведение AI-агента

- Не выдумывать данные, ставки и форматы: если источника нет — заглушка с пометкой в коде и запись
  в [memory.md](memory.md) «Открытые вопросы».
- Решения, принятые без заказчика, фиксировать в [memory.md](memory.md) «Решения» с ценой ошибки.
- Не удалять файлы и не переписывать историю без явной просьбы.
