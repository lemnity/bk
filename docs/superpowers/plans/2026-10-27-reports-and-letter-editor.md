## Task 2: Движок данных отчётов `admin-report-data.js`

Цель: единый детерминированный источник операций продажи для всех отчётов (G3).

1. `admin-report-data.js` → `window.AdminReportData`. Генерация журнала операций из `S.EVENTS`
   (мероприятия) и `S.TIERS` (зоны: `zone, seats, sold, price`). Для каждого мероприятия: дата
   представления = `event.date`; операции распределены по 30 дням до даты представления (включительно);
   объём продаж по зоне пропорционален `tier.sold` (масштабировать, чтобы суммарно было 300–1500
   операций на все события); доли видов: продажи ~85%, возвраты ~5%, брони ~6%, приглашения ~4%;
   каналы: «Касса», «Интернет», «Уполномоченный: ТЦ "Гудвин"», «Уполномоченный: Агентство
   "Афиша-Сибирь"»; кассиры (3 имени); типы оплаты «Наличные», «Карта», «СБП», «Пушкинская карта»,
   «Сертификат» с долей «Пушкинская карта» ~15% для возрастов 12+/16+ (`pk:true` только у них).
   Приглашения — цена 0. Суммы: продажа `amount = price`, возврат `amount = -price`, бронь и
   приглашение `amount = 0`. Ряд/место — правдоподобные, без повторов места внутри мероприятия+зоны.
   Операция: `{id, opDate:"YYYY-MM-DD", opTime:"HH:MM", eventId, eventTitle, eventDate, hall, genre,
   zone, row, seat, price, amount, kind, channel, cashier, pay, pk}`; `eventId` устойчивый (`ev-<индекс>`).
2. Сид ГПСЧ — хеш JSON `S.EVENTS` + `S.TIERS`: смена данных меняет журнал, повторный вызов даёт тот же
   результат. Кеш журнала сбрасывается подпиской `AdminStore.subscribe`.
3. API:
   - `ops(filter)` — `filter: {from, to (по opDate, включительно), eventFrom, eventTo (по eventDate),
     eventId, channel, pay, kind (строка или массив), pk}`; отсутствующие/пустые ключи не фильтруют.
     Возвращает копию массива, отсортированную по `opDate, opTime, id`.
   - `events()` → `[{id, title, date, hall, genre, age}]`; `channels()`, `payTypes()`, `kinds()` →
     массивы `{value, label}`; `range()` → `{min, max}` дат операций.
   - `sum(rows, key)`, `count(rows)`, `groupBy(rows, keyFn)` → `Map` в порядке первого появления.
4. Подключить `admin-report-data.js?v=1` на `report.html` и `reports.html` после `admin-store.js`.
5. Тест `tests/smoke_report_data.py`: на `report.html?no=3` через `page.evaluate`: детерминизм (два
   вызова `ops({})` дают одинаковый JSON), фильтр по периоду и `eventId` уменьшает выборку и все строки
   удовлетворяют фильтру, есть все 4 вида операций, сумма `amount` продаж > 0, возвратов < 0, ошибок
   консоли нет.

## Task 3: Виды отчётов и классификатор `admin-report-kinds.js`

Цель: каждый номер каталога открывается рабочим отчётом.

1. `admin-report-kinds.js` → `window.AdminReportKinds = { KINDS, kindOf(no), specFor(no) }`.
   Спецификация каждого вида — в формате `AdminReportSpecs` (см. шапку `admin-report-specs.js`):
   `fields` (поля из набора: период операций, период мероприятий, мероприятие (select из
   `AdminReportData.events()` + «Все»), канал, тип оплаты — какие уместны виду), `columns`
   (`key, label, num?, money?`), `rows(params)` на `AdminReportData.ops(...)`.
   Виды (минимум):
   - `byEvent` — по мероприятиям: дата, мероприятие, зал, продано шт., возвращено шт., выручка, возвраты,
     итог.
   - `byOpDate` — по датам операций: дата, продажи шт./₽, возвраты шт./₽, итог.
   - `byChannel` — по каналам (уполномоченным): канал, продано, возвраты, выручка, доля %.
   - `byPay` — по типам оплаты: тип, операций, сумма, доля %.
   - `occupancy` — заполняемость: мероприятие, зона, мест (`S.TIERS.seats`), продано, бронь,
     приглашения, свободно, заполняемость %.
   - `refunds` — журнал возвратов: дата, мероприятие, место (зона/ряд/место), сумма, канал, кассир.
   - `reserves` — брони и приглашения: дата, мероприятие, место, вид, канал.
   - `pushkin` — Пушкинская карта: мероприятие, дата, билетов, сумма.
   - `opsJournal` — детальный журнал операций — для «кассовых» отчётов.
   - `museum` — посещения (категория «Музейные»): дата, экспозиция/мероприятие, посетителей, выручка
     (из тех же операций; подписи по-музейному).
   - `orders` — категория «Приказы»: приказы о ценах, построенные из `S.EVENTS` и `S.TIERS`
     (№ приказа, дата, предмет, мероприятие, зона, цена).
   - `events` — мероприятия/репертуар из `S.EVENTS` (+ `S.RENTALS` для «Репертуар»).
   - `ledger` — «Книга операций» из `S.LEDGER`: дата, операция, статья, доход, расход; итоги — доходы,
     расходы, сальдо. Период фильтрует по дате записи (формат `DD.MM`, год 2026).
   Итоговая строка у числовых/денежных колонок, где сумма осмысленна (не у долей %).
2. `kindOf(no)`: по `cat` и регулярным выражениям по названию из `AdminReports.find(no)` (порядок
   важен): «возврат» → refunds; «брон|приглаш» → reserves; «пушкин» → pushkin; «оплат.*тип|тип.*оплат|
   безнал|эквайр» → byPay; «уполномоч|агент|распростран|мест выдачи» → byChannel; «заполн|реализованн.*
   мест|свободн.*мест» → occupancy; «по дат.*операц|за период|по дням» → byOpDate; «репертуар|^мероприятия$»
   → events; cat museum → museum; cat orders → orders; cat cash → opsJournal (если не сработало выше);
   иначе → byEvent. Таблица `OVERRIDES` для номеров, где ключевые слова ошибаются (просмотреть все строки
   каталога и заполнить по факту); `Б-1` → ledger.
3. `admin-report-specs.js`: `get(no)` — ручная спецификация, если есть («3», «3а»), иначе
   `AdminReportKinds.specFor(no)`. Добавить в `CATALOG` (`admin-reports.js`, раздел «Общие»)
   `{ no: "Б-1", cat: "general", name: "Книга операций (бухгалтерия)" }`.
4. Подключить `admin-report-kinds.js?v=1` на `report.html` (после data, до specs) и на `reports.html`.
   Поднять `?v` изменённых файлов.
5. `admin-report-view.js`: спецификация без `doc` рисуется таблицей через `renderTable` (итоговая строка);
   баннер «Параметры… не заведены» не показывается номерам, у которых есть спецификация.

## Task 6: HTML-режим письма: редактор исходника, линтер, скачивание .html

1. `admin-letter.js`: модель письма — `mode: "blocks"|"html"`, `html: string` (нормализация:
   отсутствует → `"blocks"`). `toHtml(L)` в режиме html возвращает `L.html`.
2. Вкладка «Код»:
   - режим blocks — как сейчас (только чтение) + «Редактировать как HTML» → `AdminDialog.confirm`
     («Письмо превратится в HTML-код. Блоки можно будет вернуть, но правки кода тогда пропадут.») →
     `mode="html"`, `html = toHtml(письма в блоках)`; блоки сохраняются в модели нетронутыми;
   - режим html — редактируемая textarea (моноширинный шрифт, `spellcheck=false`, Tab → 2 пробела,
     Shift+Tab снимает отступ строки), рядом живой предпросмотр `<iframe sandbox srcdoc>` (обновление
     ~300 мс после ввода), размер письма в КБ с предупреждением > 102 КБ (обрезка Gmail),
     «Вернуться к блокам» → confirm → `mode="blocks"`.
   - В режиме html палитра блоков, панель свойств и вкладка «Стиль» недоступны; «Просмотр» показывает HTML.
3. `lintHtml(html)` → `[{level:"warn"|"error", text}]`, список под редактором: нет `<table` → warn
   «Нет табличного каркаса — Outlook может разъехаться»; `<script` → error; `<link` stylesheet или
   `@import` → warn; `href="#"`/пустой `href` → warn; `src="data:` → warn «Картинки data-URL не
   показываются в Gmail/Outlook»; `width` > 600 у таблиц → warn; нет `</body>`/`</html>` → warn.
   Экспортировать `lintHtml` в `AdminLetter`.
4. «Скачать .html» рядом с «Скопировать» (в обоих режимах) — `pismo-<id или "shablon">.html`, UTF-8.
5. `admin-mailing-view.js`: сохранение/загрузка писем в html-режиме; `admin-mailings.js` — просмотр
   html-писем в списке; JSON-шаблон (выгрузка/загрузка) сохраняет `mode` и `html`.
6. Тест `tests/smoke_letter_html.py`: на `mailing.html` переход в HTML через диалог, ввод
   `<table><tr><td>Привет</td></tr></table>` → текст в предпросмотре; `<script>` → error линтера;
   «Скачать .html» → download с введённым HTML; возврат к блокам восстанавливает блоки; черновик в
   html-режиме переживает перезагрузку; iframe предпросмотра имеет `sandbox` без `allow-scripts`;
   ошибок нет.

## Task 7: Форматирование текста, переменные, отписка, кнопки без ссылки

1. Блоки `text` и `heading`: панель форматирования над полем (кнопки «Ж», «К», «Ссылка», «Список»),
   оборачивающие выделение в мини-разметку `**…**`, `_…_`, `[…](https://)`, префикс `- ` у строк.
   `richText(s)`: экранирование, затем разметка → `<strong>`, `<em>`, `<a href style>` (только
   `http(s):`, `mailto:` и `{{…}}`; прочие схемы — текстом), подряд идущие строки `- ` → `<ul>`/`<li>`
